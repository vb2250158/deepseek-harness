# DSH 环境与插件维护

面向维护 Agent。维护源代码、固定插件提交、正式安装、运行验证和清理记录，保护本地定制、未提交修改、草稿和会话。流程以本技能及其参考为唯一正文；定时任务只保存调用入口、本机绑定和触发设置。

## 入口与本机绑定

先读调用任务指定的本机 JSON 绑定。现有 Codex `dsh` 心跳默认使用 Codex 配置目录下的 `automations/dsh/maintenance-context.json`；配置目录由当前 `CODEX_HOME` 或实际用户配置确定，不猜测另一台机器的路径。绑定提供正式平台、插件源码根、临时目录、DSH Home、PR 台账、增量基线和原聊天身份，不存凭据。核对路径与实际安装；缺失或不一致时只停止依赖它的写入，继续独立只读检查。手工单项任务仅加载相关流程，不自动执行整轮更新。

Windows 保持为正式运行环境。不得因执行方便迁移到 Linux。沿用原聊天和已绑定的业务任务；活动任务正在处理相同仓库或 profile 时先核对归属，避免重复写入。互不重叠的仓库或文件范围使用多 Agent 并行；有关联的合并、安装、恢复和清理顺序执行。子 Agent 交回改动、验证、所建目录、使用者和清理条件。

## 源码 Web 交付范围

本机使用官方 Core 源码的 Web 启动入口，保留现有插件、定制和业务数据，逐项审查差异。Windows 是运行宿主，不是安装包交付要求。以官方 `dsh web` 或 `start:web` 启动，按实际改动完成所需 Host、Client、Web 编译、针对性回归与隔离启动，再切换正式服务。双端共享代码复用相应验证，不为未使用的桌面端、移动端、Python/SDK 可执行程序或 Windows 安装包追加构建与发布；这些交付仅在用户明确要求或已确认的 Web 运行依赖确实需要时执行。完整构建命令包含额外产品时，选择其现有 Web 所需步骤，不为维护重造构建框架。

日常流程保持为同步上游、按逻辑合并本地改动、针对变化验证、源码 Web 隔离启动、适用实装、远端回读和清理。仅对实际变化、真实失败或明确缺口追加检查，复用未变证据，不把日常同步扩成全产品发布。

常规同步中的实现选择、合并适配和缺陷修复由维护 Agent 自主完成，不等待用户逐项取舍；只对超出既有授权的具体事项请求决定，并继续其余工作。

## 固定环境测试标准

只保证本维护 fork 在仓库声明的当前宿主和环境版本上运行正常。仓库列明宿主版本、源码运行方式、操作系统与架构、Node 和包管理器版本；受测候选与正式在用状态分开记录。变更宿主或环境时同步更新声明，再验证实际使用的组合。

本地及本 fork 的自动 CI 不执行旧 DSH、多 Node、多操作系统或其它未使用产品的兼容矩阵，不为通过这些组合增加兼容分支或重复安装旧宿主。保留当前版本的行为回归、实际已有数据的读写与保留、必要构建、源码 Web 启动及真实加载来源验证；不删除仍能发现当前版本问题的断言。未变化且仍匹配声明环境的结果直接复用。

公开代码不代表承诺维护所有环境。其它环境等社区给出具体反馈或 PR 后，按复现条件、改动影响和现有版本回归评审，适用验证通过再按仓库流程合入；不预先扩建兼容矩阵。提交上游时只执行该候选实际适用且上游要求的检查，不能将其全平台发布流程变成本机日常维护要求。

## 插件主分支工作流

插件开发、更新、修复和验收沿用仓库现有主分支（main 或实际 master），不新建本地或远端插件分支。先把交接中的独有改动按逻辑合入主分支，完成验证、实装和远端回读后，按[清理流程](references/cleanup.md)删除已合并且无人使用的分支和副本。隔离验收使用独立 profile、端口、数据目录或无分支的源码导出。既有未合并 PR 分支保留到原任务完成。按用户授权，通用且已验证的最小上游修复可建立临时贡献分支并提交 PR，无需逐次询问；贡献分支从当前上游建立并逐项登记跟进。PR 合并或关闭后，确认贡献已归档、无独有未保存修改及使用者，再清理临时贡献分支和副本。跨机开发沿用维护主分支，共享清单固定已验收提交。

## 插件修复授权

- 处理本项目任务时，官方、自维护和第三方插件发现并确认 Bug 后，可自主定位、修复和验证，无需逐次申请修复权限。在源码所属仓库修改，保留无关改动，避免只改安装产物。
- 遵循所属仓库规范，完成适用回归验证；涉及运行行为时核对实际加载版本和运行效果。
- 具有通用价值、验证通过且适合公开贡献的修复，可整理最小改动、提交推送并向对应上游提交 PR；分支创建遵守上述主分支工作流。按上游要求组织最小代码、测试和文档，排除凭据、私人配置及无关改动。PR 合并与正式发布遵循各自授权；本技能不自动授予其它项目或账号权限。

## 每轮执行

1. 读取上轮仓库提交、插件固定 pin、安装和运行摘要、验证结果、PR 台账及未清理项。优先续接未完成的候选、正式交付、共享配置发布和清理，即使没有新上游提交也继续处理可行动缺口。批量完成独立只读检查，按实际目录发现全部维护仓库，不能只依赖旧索引数量或最近修改的插件。
2. 每轮先读取全部活跃 PR 的反馈与状态，并补查本账号历史提交，见 [上游贡献与跟进](references/upstream-prs.md)。已有稳定候选即使没有新上游提交，也要评估。
3. 对实际变化或明确证据缺口执行 [更新、同步与 Windows 交付](references/update-delivery.md)：在所属源码修复验证发现的问题，针对性重测，通过当前完整正式组合的隔离源码 Web 验收后实装，回读运行来源与数据，再完成共享配置发布和清理。逐仓库、逐提交和逻辑合并，保护本地改动。复用未变化且仍适用的证据，不为提交或推送重复测试，不对未变化环境重复安装、重启。
4. 每轮覆盖全部插件的分支、工作树和本地文件，处理本轮及历史遗留，见 [目录、分支与空间回收](references/cleanup.md)。不能只检查新建目录。
5. 在现有台账中分别记录源码、隔离验收、正式运行、共享远端和清理的实际状态、证据及未完成项的负责人和下一动作，保存最小可恢复基线、各插件贡献评估和 PR 处理结果。写入前留底、同步最新内容，按仓库和 PR 稳定身份合并，写后回读，避免并发覆盖。

## 完成与通知

分别报告源码合并、提交推送与远端 SHA、正式安装来源、实际运行验收、共享配置远端回读、PR 状态及清理结果。源码测试、上传或依赖导入成功只闭合对应步骤；全部适用交付、运行验收及清理完成才报告整轮完成。仍有当前人类暂停、活动业务、权限、法律协议或占用等阻点时，记录具体对象、原因和恢复条件，仅停止相关动作并继续其它独立工作。

无实际更新、可行动反馈或状态变化时保持安静，包括排队、仍在运行、等待审批等未变化状态。完成实际更新、创建或实质更新 PR、审查审批有实质进展、检查失败或修复、合并关闭、发生失败或需要用户决定时通知，附证据及对应 PR 链接。心跳调用按宿主规定返回 `NOTIFY` 或 `DONT_NOTIFY`，不因触发本身发送例行进度。仅在用户要求调整定时任务时修改现有自动化，保留未要求变更的时间、状态、原聊天和通知偏好。
