# 上游贡献与持续跟进

完整每日维护均读取本参考；手工任务仅在贡献或 PR 跟进范围内使用。已授权的 PR 内回复仅用于本流程相关问题，不扩展为其它渠道联络。

## 候选评估

1. 确认每个插件真正的原始上游、公开或私有属性、许可证及贡献要求。上游不接受外部 PR 或存在贡献限制时记录依据，不擅自改发 Issue、Discussion 或联系维护者。
2. 比较最新默认分支，逐提交和逻辑审查差异，并查重 open、merged、closed PR。排除上游已实现或维护者明确拒绝的重复内容。无新上游提交也检查此前完成且稳定运行的候选。
3. 自研插件判断应继续独立发布、贡献插件生态文档，还是确需向 DSH 官方提交最小公共修复；不把整套插件或个人定制直接塞入官方。
4. 通用用户价值明确、方案足够小、兼容性明确，且有相应回归测试和实际稳定运行证据的改动，可按本项目授权整理并提交 PR，无需逐次询问。刚安装、仅有源码测试或验收不足的先补验证或保留观察；不为凑 PR 提交版本号、锁文件噪声和个人偏好。
5. 保护维护分支、未提交文件和草稿，从当前上游建立独立贡献分支，按主题只带必要代码、测试和文档。脱敏、适用检查和差异复核完成后推送创建 PR。私有代码、凭据、内部地址、账号、本机配置、会话和资源未经单独授权不得公开；新法律协议、版权授权或超出范围的决定只停止相关候选，说明具体缺口。

## 台账与发现

使用本机绑定的 `prRegistry`，按仓库及 PR 编号记录链接、贡献分支和 head、最后检查时间、审核审批结论、未解决线程、CI 与权限等待、冲突、已处理评论稳定身份、下一动作及终态原因。保留可恢复历史；仅存必要元数据和处理摘要，不保存凭据或完整敏感评论。现有台账和绑定中的历史 PR 是起点，不是数量上限。

每轮从当前账号在维护范围各上游发起的 PR 列表补查，覆盖分页，合并登记遗漏项和以后新建项。逐个跟进全部活跃 PR，不只看最近一个；已确认终态退出活跃队列但不删除历史。各插件另保留“提交、暂缓、独立发布”的评估及理由。

## 审查、修复与回读

1. 批量读取每个活跃 PR 最新 reviews/审批、普通评论、未解决 review threads、review requests、CI、base/head、可合并性和合并/关闭状态；所有分页读完再判断。区分当前 head 的批准与旧批准，未报告检查不算 CI 通过，批准不等于合并。
2. 按冲突、有效审查意见、失败 CI 的顺序处理。写前同步最新贡献分支和上游，保护他人提交与维护分支；确认范围内问题后最小修复、针对验证、普通推送。禁止强推、删除检查或弱化断言求通过。
3. 在对应 PR 回复处理结果和提交；不成立或已失效的意见说明具体理由，按权限正确处理线程。记录已处理评论的稳定身份，避免重复回复或催促。
4. 需要维护者批准工作流、缺权限、新法律协议或超出范围决定时，记录具体阻点，继续其它 PR。不代替上游审核，不自动合并，不擅自改变可见性或重新打开已关闭 PR。
5. 创建或实质更新 PR 后，回读目标仓库、base/head、实际差异、链接和检查状态，并关联到本聊天。回复或处理线程后再回读新 head、评论回执、线程与检查状态，更新台账。
6. 合并后核对实际合入提交，交正常同步流程评估本地补丁能否移除；未合并而关闭的先读原因，保存结论再退出活跃队列。
